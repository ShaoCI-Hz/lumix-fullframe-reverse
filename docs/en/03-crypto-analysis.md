# DC-S5M2X Firmware Encryption Analysis

Samples: `S5m2XV27.bin` (DC-S5M2X), `S5m2_V37.bin` (DC-S5M2 sister model)

---

## 1. Encryption scheme (established)

| Item | Finding | Evidence |
|---|---|---|
| Cipher type | **AES-CTR-class stream encryption** | block uniqueness 100%, keystream entropy 7.997 |
| nonce/IV | **12 bytes**, stored in the partition table at `+0x4C` | standard GCM length; cross-model verified |
| Integrity check | **SHA-256**, stored in the partition table at `+0x2C` | verified on plaintext partitions |
| Key | **model-dependent** (not global) | same IV + same plaintext → different ciphertext |

### Encryption determination

| flags | State | Partitions |
|---|---|---|
| 3 | **encrypted** | `loader1` `program` `compress_pr` `postboot*` `eep_ow_*` `music` `osd*` `hm_*` `hr_*` |
| 2 | mostly empty/plaintext | `wifi*` `menu_save` `lut_data` `xtk` `kizu_data` (all zero) |
| 2 | **encrypted** | `lens_hist` (the one counterexample: entropy 8.00, digest points at all-zero) |

> `flags` is not a strict encryption flag; whether a partition is encrypted must
> be decided by comparing the image bytes against the SHA-256 digest.

---

## 2. Digest semantics (`+0x2C` = SHA-256)

**The digest is `SHA-256(plaintext)`**, not a hash of the image ciphertext.
Verified:

| Partition | Digest | Meaning |
|---|---|---|
| `lut_data` and other all-zero partitions | `SHA-256(image)` | plaintext = image = all zero |
| `boot` (all 0xFF) | `SHA-256(empty)` = `e3b0c442…` | erased state counts as no content |
| `lens_hist` (image entropy 8) | `SHA-256(all-zero)` | **plaintext is all zero; the image is ciphertext** |
| `menu_save` | `3b874d3b…` | factory default content (image is empty) |

> **This is the yardstick for decryption**: after any decryption attempt,
> comparing `SHA-256(result)` against `+0x2C` gives a deterministic verdict.

---

## 3. Partition structure

- **A/B redundancy**: `eep_ow_a/b`, `eep_act_a/b`, `eep_exp_a/b` hold identical
  content with different IVs (embedded redundancy)
- Layout: `UPD header (0x0)` + `partition table (0x2DC, 58 × 92B)` + `data area (0x80000+)`
- `+0x40` = `CRC32(d[0x200 : end])` — header checksum established

---

## 4. Cross-model diff (S5M2X vs S5M2)

The two firmwares are **exactly the same size** (179,207,168 B) and differ in the
model ID only (`MC8223X` / `MC8223`).

**Decisive finding**:
```
lens_hist   same plaintext (all zero)   same IV (all zero)   different ciphertext
            <- same IV and same plaintext, yet different ciphertext
```
Deterministic encryption (same key + same IV + same plaintext) must produce the
same ciphertext. It does not here, which **proves the key is model-dependent** —
presumably derived from the model ID or unique to the hardware.

## 6. Assessment and suggestions

**The AES key is not obtainable through software alone** — it is not simply
derived (see §9) and is most likely generated by hardware or a complex KDF;
AES-256 has no feasible cryptanalytic attack. The firmware data partitions
remain ciphertext under read-only analysis, with no exploitable leak found.

### Directions for further study

1. **Protocol-layer observation (PTP)** — the camera is already in tether mode
   (PID `2382`); vendor command behaviour and responses can be recorded and
   analysed without any key.

2. **Runtime observation** — if the protocol exposes runtime state,
   post-decryption behaviour can be observed.

3. **Hardware-side observation** — requires physical access and specialised
   equipment; not covered here.

### On how feature configuration is stored

`menu_save` (the feature-configuration area) is empty inside the firmware
image; **the actual state is decided at runtime by logic in `program`**, and
`program` is ciphertext, so that logic is not visible under static analysis.
The observation shows: **the image itself contains no readable feature
configuration data**.

## 8. Final analysis of the encryption structure (static avenues exhausted)

### 8.1 Block structure: 64 KB (0x10000) encryption blocks

| Partition | First non-zero offset in partition | First block non-zero/entropy | Subsequent blocks | Logical plaintext |
|---|---|---|---|---|
| `grid_data` | `0x147A00` | 34,177 / **5.165** | 65,280 / **7.997** | all zero |
| `vkizu_data` | `0x527A00` | 34,178 / **5.165** | 65,300 / **7.997** | all zero |
| `lut2_data` | `0x767A00` | 34,180 / **5.166** | 65,290 / **7.997** | all zero |
| `lens_hist` | `0x0` | 65,278 / **7.997** | full block | all zero |

**Patterns**:
1. Data start offsets **all end in `0x7A00`** (`0x147A00`/`0x527A00`/`0x767A00`)
2. Inside each 64 KB block the ciphertext is full-entropy (ent ≈ 7.997)
3. The boundary block is **half-full**, leaking the effective data length

### 8.2 The apparent "low entropy" is a zero-padding artifact

| Partition | Surface entropy | **After excluding zero padding** | Non-zero share |
|---|---|---|---|
| `eep_fix` | 2.688 | **7.988** | 23.75% |
| `hr_d_prog` | 3.356 | **7.993** | 30.83% |
| `grid_data` | 4.419 | **7.994** | 42.95% |
| `osddata` | 7.906 | **7.974** | 96.28% |

**The entropy of the non-zero part is ≥ 7.988 everywhere — no plaintext leak.**
Partition structure = `[encrypted data] + [zero padding (0x00 flash-erased state)]`.

### 8.3 nonce / plaintext

- **43 non-zero nonces, 0 repeats** — no nonce-reuse opportunity
- 9 partitions have `nonce=0` and their ciphertext prefixes **all differ** →
  each partition has its own subkey; the nonce is not just `+0x4C`
- 4 partitions have **known all-zero plaintext** (digest = `SHA-256(all-zero N)`):
  `lens_hist` `vkizu_data` `lut2_data` `grid_data`
  → their **ciphertext is the keystream**, useful as decryption-verification
  samples, but the nonces differ and are not interchangeable

### 8.4 Static analysis conclusions (exhausted)

| Analysis path | Result |
|---|---|
| Key enumeration | ❌ AES; key not in the firmware (model-dependent) |
| ECB repeated blocks | ❌ zero repeats, uniqueness 1.0 |
| Compression (retested after fixing the offset) | ❌ all fail |
| nonce reuse | ❌ 43 nonces, no repeats |
| Plaintext leakage | ❌ non-zero entropy ≥ 7.988 everywhere |
| Known plaintext | ⚠️ 4 all-zero samples, but distinct nonces make them non-interchangeable |
| Simple key derivation | ❌ model ID + UPD header fields all fail |

**The data itself leaks nothing**: high entropy, unique nonces, key external
and model-dependent.

**Observation directions**:
1. **Runtime memory observation** — decrypted firmware resides in RAM
2. **Hardware-side observation** — requires physical access and specialised equipment
3. **Protocol-layer observation** — recording device–host interaction (camera must be online)

## 9. Supplementary static attempts (all failed)

Systematic attempts made after the §8 conclusion, recorded here to save others
the repetition:

### 9.1 Keystream-reuse search — ❌

The four known-all-zero-plaintext partitions (lens_hist / vkizu_data / lut2_data /
grid_data) have ciphertext equal to the keystream. Searching 64-byte probes
across the whole firmware: **each probe hits only at its own position** — no
cross-partition or cross-model reuse.

### 9.2 Data-area aligned comparison — ❌

After correcting the sampling error of using the partition start (zero padding)
instead of the data-area start: the four partitions' data-area ciphertexts show
**256/256 differing XOR values**, with 0 identical 16 B blocks. **No reuse.**

### 9.3 Two-model diff (S5M2X vs S5M2) — ❌

| Partition | Ciphertext XOR | Identical 64 B blocks |
|---|---|---|
| lens_hist | 256/256 differing values | 0 |
| other all-zero partitions | leading section all zero (padding) | — |

Non-zero nonces have **0 repeats**. The key is model-dependent, so the diff
leaks nothing.

### 9.4 Systematic nonce/key derivation — ❌

Combinations enumerated:
- Key sources: partition name / model ID / `name+model` / `model+name` / `sha256(name+tail3)` / `md5` / `sha1` / zero padding
- nonce sources: `+0x4C` (12B) / `+0x58` (4B) / partition index / offset / size / `sha256(name)[:12]` / tail3
- CTR layouts: `nonce+counter` / `counter+nonce` / `full16`
- Endianness: little/big; key lengths: 128/192/256

**No match at all.**

### 9.5 Newly found structure (valuable, but yields no key)

**a) Three bytes hide behind the partition entry's name field** (`+0x1D`),
previously unparsed:

```
Partition entry layout (92 bytes):
  +0x00  u32 x4  all zero
  +0x10  13B     name (ASCII, \0 padded)
  +0x1D  3B      address-space tag   <- newly found
  +0x20  u32     size
  +0x24  u32     offset
  +0x28  u32     flags
  +0x2C  32B     SHA-256 (plaintext)
  +0x4C  12B     nonce/IV
  +0x58  u32     0
```

The 3 bytes at `+0x1D` split into two address spaces:
```
0x16xxxx group (boot/loader*/storage/program/postboot*/eep_*/compress_pr)   <- system area
0x7Axxxx group (lens_hist/lut*/osd*/music/wifi*/menu_save/grid/hm_*/dsp_*)  <- data area
```

**b) The 64 KB pattern of data start offsets**:
```
grid_data   data start mod 64K = 0x7A00,  length mod 64K = 0x8600
vkizu_data  same
lut2_data   same
0x7A00 + 0x8600 = 0x10000 (64KB)
lens_hist   data start mod 64K = 0x0 (the only exception)
```

### 9.6 Conclusion

**Static avenues are thoroughly exhausted.** The cipher is strong (AES-class),
with per-partition nonces/subkeys; the key material is not in the firmware
(model-dependent, presumed to live in an SoC secure area or ROM).

**The data leaks nothing usable:**
- non-zero entropy ≥ 7.988 (no plaintext)
- no nonce repeats (no reuse opportunity)
- known plaintext (all zero) is non-interchangeable because the nonces differ

**Further observation requires leaving the static file:**

1. **Runtime memory observation** — decrypted firmware resides in RAM
2. **Hardware-side observation** — requires physical access and specialised equipment
3. **Protocol-layer observation** — recording device–host interaction (camera must be online)

> Note: the above is not "nothing was found" but "the firmware file contains no
> exploitable cryptographic material". The metadata (the `+0x2C` digest in the
> partition table) is by design a **decryption yardstick** usable to verify any
> decryption attempt.

## 10. Decisive finding: UPD = encryption + signature, twofold protection

### 10.1 Complete UPD header semantics (fully parsed)

| Offset | Size | Meaning |
|---|---|---|
| `+0x000` | 4 | `"UPD\0"` magic (0x00445055) |
| `+0x004` | 4 | block size = 512 |
| `+0x008` | 4 | block size = 512 |
| `+0x00C` | 16 | model ID (`MC8223X` / `MC8223`) |
| `+0x01C` | 4 | `0x02740274` |
| `+0x020` | 4 | `0x00010004` |
| `+0x024` | 4 | **version/date field** (X=`0x02102019`, M=`0x02102018`) |
| `+0x02C` | 4 | 3 |
| `+0x034` | 4 | 3 |
| `+0x038` | 4 | 512 |
| `+0x03C` | 4 | image_data_size = 179,206,656 |
| `+0x040` | 4 | CRC32(data area `[0x200..end]`) |
| `+0x200` | 16 | `"panasonic"` marker + padding |
| **`+0x220`** | **64** | **ECDSA P-256 signature (r‖s)** ← key finding |
| `+0x2A0` | 512 | second UPD record (**identical** to `0x0`, redundant copy) |

### 10.2 The 64 bytes at 0x220 are an ECDSA P-256 signature

```
S5M2X: r = 0x6601F80A9B158E0D2ACCF8C082AF148910F4E9D31D19E9122444AAE70309C022
       s = 0x504E685692529ABB585542841200A75FD92E87A10A2EDD31484111DCE35EE1ED
S5M2 : r = 0x1AAC8FFDC7BA7EFD2A960E9AD6CAA7709C0FBECB8F1739CC264F4AEB82DF4558
       s = 0xECA69487786CC66BF762686BED7A9F4149C636F2380956E92E6F2385B8CD3B74
```

**Verification basis**:
- both `r` and `s` satisfy `1 <= r,s < N` (N = P-256 curve order)
- S5M2X's `s <= N/2` (low-s normalisation, a canonical signature trait)
- the two models are **completely different** (each firmware has its own signature)

**Verdict: an ECDSA P-256 digital signature**, used for firmware
integrity/provenance verification.

### 10.3 ⚠️ Decisive implication: modifying the image is not viable

```
AES encryption     -> prevents reading/analysing the code
ECDSA P-256 sig    -> prevents tampering with the firmware
```

**Even with AES plaintext and a modified `program`, the signature check would
reject the image.** The ECDSA private key lives with the vendor and is not
obtainable → **image integrity is guaranteed by the signature, and a modified
image cannot pass verification.**

### 10.4 Analysis paths ruled out in this round (all ineffective, conclusions clear)

| Analysis path | Result |
|---|---|
| keystream-reuse search | ❌ each probe hits only its own position |
| Data-area aligned comparison (after fixing the sampling error) | ❌ 256/256 all differ |
| Two-model keystream diff | ❌ fully random |
| Systematic nonce/key derivation (partition name × tail3 × model × layout × endianness) | ❌ no hit |
| **Dictionary attack** (every short string in the firmware as key) | ❌ 100k+ combinations, no hit |
| **Common plaintext pattern guessing** (all-0/all-FF/incrementing/repeated blocks) verified by digest | ❌ only "all zero" hits |
| **UPD header 64 bytes as key** | ❌ that is the signature, not a key |
| Keystream randomness testing | **entropy 7.9995, chi-square 274.5, no autocorrelation, block uniqueness 1.0** → strong cipher confirmed |

### 10.5 Further structural findings

- **`menu_save` logical content = all `0xFF`** (digest = SHA-256(all-FF)) while
  the image is all zero → proving the digest describes "what should be there",
  not the image bytes
- **The 3 bytes after the partition entry's `name` = flash address-space tag**:
  `0x16xxxx` (system area) / `0x7Axxxx` (data area)
- **Data start offset pattern**: `N×0x10000 + 0x7A00`, with `0x7A00 + 0x8600 = 64KB`

### 10.6 Final conclusion

**Static analysis has reached its limit** (AES strong encryption + ECDSA
signature). Further effort on the firmware file will not produce results — this
is not "nothing was found" but **"no exploitable information exists in the file"**.

**The protocol layer can be observed without modifying the firmware** (involving
neither encryption nor signature handling).

## 11. Dissecting the old platform + plaintext partition directory (new findings)

### 11.1 Old-platform architecture (Linux)

The S1/S1H/S5 partition tables contain Linux system components:
```
zimage(2.6MB kernel) dtb(device tree) rootfs1/rootfs2(filesystems)
zboot apu0_code/data_i/e ipu_rc_nr_code/data  mult_fpga(S1H) / lns_fpga(S1)
```
**But all of it is encrypted** (entropy 8.000; every decompression test fails),
including `zimage`/`rootfs`.

### 11.2 ★ New finding: loader2/loader3 embed a plaintext partition directory

`loader2` **begins with a plaintext structure** (4-byte header + N × 92-byte entries):

```
S1H loader2 (38912 B):
  #  name          A(flash addr)  size        B           flg  hash[:8]
  0  nr_data       0x0499BC00      262,144  0x04E60000    3   e235e388...
  1  nr_code       0x049DBC00       65,536  0x04EA0000    3   2553aa1d...
  2  hm_c_prog     0x049EBC00       65,536  0x04EC0000    3   06e44fbb...
  ...
  10 hr_c_ddr      0x0568BC00      262,144  0x05B80000    3   dda4ddd0...

  -> all 11 entries' size and hash match the main partition table exactly
```

**Entry structure (92 bytes)**:
```
+0x00  12B   name
+0x0C  u32   A (flash address)
+0x10  u32   size
+0x14  u32   B (another address, possibly the RAM load address)
+0x18  u32   flags (=3)
+0x1C  32B   SHA-256 (plaintext content hash, same as the main partition table)
```

**Meaning**: the load table for co-processor programs (nr_/hm_/hr_), stored in
**plaintext**.

### 11.3 The image is a "true flash re-layout" package

Comparing `loader2.A` (flash address) with the partition table's `off` (image
position):

| Partition | loader2 A | image off | Difference |
|---|---|---|---|
| nr_data | 0x0499BC00 | 0x04E60000 | 0x4C4400 |
| hm_c_prog | 0x049EBC00 | 0x04EC0000 | 0x4D4400 |
| hm_d_ddr | 0x04D3BC00 | 0x05220000 | 0x4E4400 |
| hr_c_ddr | 0x0568BC00 | 0x05B80000 | 0x4F4400 |

**The difference increases in steps of 0x10000 (64 KB)** →
1. the tight packing inside the image results from re-laying out a
   "64 KB-aligned flash allocation"
2. this reconfirms the **64 KB block structure**

### 11.4 Conclusion

**The firmware carries several layers of integrity metadata** (all plaintext):
```
main partition table (58 entries, SHA-256 + nonce + flags)
loader2/loader3 directory tables (A/B addresses + SHA-256)
UPD header CRC32
ECDSA P-256 signature
```

**Yet there is still no key material.** All partition data (including
`zimage`/`rootfs`) is encrypted, and plaintext exists only in the **metadata
layer**. Static analysis still does not expose plaintext.

`old_decompress.py`, `loader2_dir2.py`, `addr_check.py`, `gap_analysis.py`

## 12. Blind-spot sweep and self-correction (final conclusion on the encryption)

### 12.1 Three previously unchecked blind spots (each ruled out)

| Blind spot | Check result |
|---|---|
| The 16 bytes at partition entry `+0x00..+0x10` | **essentially all zero** (of 53 entries only `loader1` is non-zero, containing image metadata: total size `0x056CBC00` + partition count `0x35`=53, not a key) |
| `loader2` remainder (37,896 B after the directory table) | **also encrypted data** (see 12.2) |
| `loader3` in full (49,152 B) | **also encrypted data** |
| All UPD header fields `+0x00..+0x80` | all known metadata, no key material |

### 12.2 ★ A self-correction: small entropy windows mislead

While analysing the `loader2` remainder, 256-byte windows gave entropy
**7.0–7.3**, which was briefly misread as "compressed rather than encrypted".
**Recomputing over the whole block gives 7.9954**, consistent with known
encrypted data:

| Metric | loader2 remainder | program (known encrypted) | Random theoretical |
|---|---|---|---|
| Whole-block entropy | **7.9954** | 7.9973 | 8.0 |
| Chi-square (256 buckets) | 240.0 | 241.9 | ≈255 |
| Zero-byte share | 0.3853% | 0.382% | 0.3906% |
| Adjacent-equal share | 0.3800% | 0.377% | 0.3906% |
| 4-byte-aligned zero u32 | 0.02% | — | ≈0 |

**Conclusion: the region is encrypted data; there is no compressed stream or
plaintext structure.** Entropy over a small window (a few hundred bytes)
fluctuates too much to decide a format — noted in the script comments so others
do not repeat the mistake.

### 12.3 Decompression paths attempted (all failed)

For `loader1`/`loader2`/`loader3` at several starting points
(`0x0`/`0x4`/`0x3F8`/`0x400`/`0x1000`):
`zlib` (wbits 15/-15/31/47), `gzip`, `lzma` (AUTO/XZ/ALONE/RAW-LZMA1/RAW-LZMA2),
`bzip2`, `zstd` — **none succeeded**.

### 12.4 Final conclusion

**The static analysis path is exhausted; no viable approach remains.** Basis:

```
1. every data partition is encrypted   -- including loader / zimage / rootfs, no exception
2. plaintext exists only in metadata   -- partition table / loader2 directory / UPD header / ECDSA signature
3. the key is not simply derived       -- 6 models x multiple keystream samples, 17,496 combinations all failed
4. per-model, per-partition keys       -- identical nonce, size and plaintext yield 100% different ciphertext across models
5. even if decrypted                   -- it still would not pass the ECDSA P-256 signature check
```

**This is not "not found" — it is the result of repeated verification across
multiple models, samples and algorithms.**

2. **Hardware-side observation** — the old platform runs embedded Linux; requires physical access and specialised equipment, not covered here
3. **USB/PTP protocol layer** — protocol-layer observation that does not touch the firmware (camera must be online)
