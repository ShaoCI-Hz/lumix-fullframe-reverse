# DC-S5M2X 固件加密分析

样本:`S5m2XV27.bin`(DC-S5M2X)、`S5m2_V37.bin`(DC-S5M2 姊妹机型)

---

## 1. 加密方案(已确定)

| 项 | 结论 | 依据 |
|---|---|---|
| 加密类型 | **AES-CTR 类流加密** | 块唯一率 100%,keystream 熵 7.997 |
| nonce/IV | **12 字节**,存于分区表 `+0x4C` | GCM 标准长度;跨机型验证 |
| 完整性校验 | **SHA-256**,存于分区表 `+0x2C` | 明文分区验证通过 |
| 密钥 | **与机型相关**(非全局) | 同 IV 同明文 → 不同密文 |

### 加密判定

| flags | 状态 | 分区 |
|---|---|---|
| 3 | **加密** | `loader1` `program` `compress_pr` `postboot*` `eep_ow_*` `music` `osd*` `hm_*` `hr_*` |
| 2 | 多为空/明文 | `wifi*` `menu_save` `lut_data` `xtk` `kizu_data`(全零) |
| 2 | **加密** | `lens_hist`(唯一反例:熵 8.00,摘要指向全零) |

> `flags` 并非严格的加密标志;加密与否需按"镜像字节 vs SHA-256 摘要"判断。

---

## 2. 摘要语义(`+0x2C` = SHA-256)

**摘要 = `SHA-256(明文)`**,不是镜像密文的哈希。已验证:

| 分区 | 摘要 | 含义 |
|---|---|---|
| `lut_data` 等全零分区 | `SHA-256(镜像)` | 明文 = 镜像 = 全零 |
| `boot`(全 0xFF) | `SHA-256(空)` = `e3b0c442...` | 擦除态视为无内容 |
| `lens_hist`(镜像熵 8) | `SHA-256(全零)` | **明文全零,镜像是密文** |
| `menu_save` | `3b874d3b...` | 出厂默认内容(镜像为空) |

> **这是解密的验证标尺**:任何解密尝试后,`SHA-256(结果)` 与 `+0x2C` 比对即可确定性判定正误。

---

## 3. 分区结构

- **A/B 双备份**:`eep_ow_a/b`、`eep_act_a/b`、`eep_exp_a/b` 内容相同、IV 不同(嵌入式冗余)
- 布局:`UPD 头(0x0)` + `分区表(0x2DC,58 项 × 92B)` + `数据区(0x80000+)`
- `+0x40` = `CRC32(d[0x200 : 末尾])` ← 头部校验已确定

---

## 4. 跨机型差分(S5M2X vs S5M2)

两固件**大小完全一致**(179,207,168 B),机型 ID 仅差 `MC8223X` / `MC8223`。

**决定性发现**:
```
lens_hist   明文同(全零)  IV同(全零)  密文不同  ←  同 IV 同明文却密文不同
```
确定性加密(同 key 同 IV 同明文)必须产生相同密文。这里不同,
**证明密钥与机型相关**,推测由机型 ID 派生或硬件唯一。

## 5. 已排除的分析路径

| 路径 | 结果 |
|---|---|
| ECB 重复块分析 | ✗ 零重复,块唯一率 1.0 |
| 压缩(lzma/zstd/zlib/bz2) | ✗ 全部解压失败 |

| 明文泄露 | ✗ 有数据分区均加密 |
| 简单密钥派生 | ✗ 机型 ID + UPD 头字段 + 常见 KDF 全部失败 |

## 6. 评估与建议

**纯软件途径无法获得 AES 密钥** —— 密钥非简单派生(详见 §9),
大概率由硬件或复杂 KDF 生成,AES-256 无可行的密码分析路径。
固件数据分区在只读分析下保持密文,未发现可利用的信息泄露。

### 后续可研究的方向

1. **协议层观察(PTP)** —— 相机已切 tether 模式(PID `2382`),
   可记录并分析厂商命令的行为与响应,不依赖密钥。

2. **运行时观察** —— 若协议允许读取运行时状态,可观察解密后的运行行为。

3. **硬件侧观察** —— 需物理访问与专业设备,此处不展开。

### 关于功能配置的存储

`menu_save`(功能配置区)在固件镜像内为空,**实际状态由 `program` 中的逻辑在运行时决定**,
而 `program` 为密文,故该逻辑在静态分析下不可见。
这一观察说明:**镜像本身不包含可读的功能配置数据**。

## 8. 加密结构最终解析(静态攻击已穷尽)

### 8.1 块结构:64KB (0x10000) 加密块

| 分区 | 分区内非零起始 | 首块非零/熵 | 后续块 | 逻辑明文 |
|---|---|---|---|---|
| `grid_data` | `0x147A00` | 34,177 / **5.165** | 65,280 / **7.997** | 全零 |
| `vkizu_data` | `0x527A00` | 34,178 / **5.165** | 65,300 / **7.997** | 全零 |
| `lut2_data` | `0x767A00` | 34,180 / **5.166** | 65,290 / **7.997** | 全零 |
| `lens_hist` | `0x0` | 65,278 / **7.997** | 满块 | 全零 |

**规律**:
1. 数据起始偏移**全部以 `0x7A00` 结尾**(`0x147A00`/`0x527A00`/`0x767A00`)
2. 每个 64KB 块内部满熵密文(ent≈7.997)
3. 边界块**半满**,泄露有效数据长度

### 8.2 "低熵"是零填充假象

| 分区 | 表面熵 | **排除零填充后** | 非零占比 |
|---|---|---|---|
| `eep_fix` | 2.688 | **7.988** | 23.75% |
| `hr_d_prog` | 3.356 | **7.993** | 30.83% |
| `grid_data` | 4.419 | **7.994** | 42.95% |
| `osddata` | 7.906 | **7.974** | 96.28% |

**非零部分熵全部 ≥ 7.988,无任何明文泄露。**
分区结构 = `[加密数据] + [零填充(0x00 flash 擦除态)]`。

### 8.3 nonce / 明文

- **43 个非零 nonce,0 重复** — 无 nonce 重用攻击机会
- `nonce=0` 共 9 个分区,密文前缀**互不相同** → 各分区独立子密钥,nonce 不仅是 `+0x4C`
- 4 个分区**明文已知为全零**(摘要 = `SHA-256(全零N)`):
  `lens_hist` `vkizu_data` `lut2_data` `grid_data`
  → 其**密文即 keystream**,是解密验证样本,但 nonce 各异不可互换

### 8.4 静态分析结论(已穷尽)

| 分析路径 | 结果 |
|---|---|
| 密钥穷举 | ❌ AES,密钥不在固件(机型相关) |
| ECB 重复块 | ❌ 零重复,唯一率 1.0 |
| 压缩(修正偏移后重测) | ❌ 全部失败 |
| nonce 重用 | ❌ 43 个 nonce 无重复 |
| 明文泄露 | ❌ 非零熵全 ≥7.988 |
| 已知明文 | ⚠️ 4 个全零样本但 nonce 各异,不可互换 |
| 简单密钥派生 | ❌ 机型 ID + UPD 头字段全试失败 |

**数据本身不泄露任何信息**:高熵、nonce 唯一、密钥外部(机型相关)。

**观察方向**:
1. **运行时内存观察** — 解密后固件驻留 RAM
2. **硬件侧观察** — 需物理访问与专业设备
3. **协议层观察** — 记录设备与主机的交互(需相机在线)

## 9. 静态分析的补充尝试记录(全部失败)

在「§8 结论」之后又做了系统性尝试,记录如下以免后人重复:

### 9.1 keystream 复用搜索 — ❌

4 个明文全零分区(lens_hist / vkizu_data / lut2_data / grid_data)的密文即 keystream。
取 64 字节探针在全固件搜索:**每个探针只在自己位置命中**,无跨分区/跨机型复用。

### 9.2 数据区对齐比较 — ❌

修正「用分区起始(零填充)而非数据区起始」的取数错误后重比:
四个分区数据区密文 **XOR 差异 256/256 个不同值**,相同 16B 块 = 0。**无复用**。

### 9.3 两机型差分(S5M2X vs S5M2) — ❌

| 分区 | 密文 XOR | 相同 64B 块 |
|---|---|---|
| lens_hist | 256/256 不同值 | 0 |
| 其余全零分区 | 前段全零(填充) | — |

非零 nonce **0 重复**。密钥与机型相关,差分无泄漏。

### 9.4 系统性 nonce/key 派生 — ❌

已穷举组合:
- 密钥源:分区名 / 机型 ID / `name+model` / `model+name` / `sha256(name+tail3)` / `md5` / `sha1` / 零填充
- nonce 源:`+0x4C`(12B)/ `+0x58`(4B)/ 分区索引 / 偏移 / 大小 / `sha256(name)[:12]` / tail3
- CTR 布局:`nonce+counter` / `counter+nonce` / `full16`
- 字节序:大小端;密钥长度:128/192/256

**全部未匹配。**

### 9.5 新发现的结构(有价值,但不给密钥)

**a) 分区项 name 字段后藏着 3 字节**(`+0x1D`),此前未解析:

```
分区项布局(92 字节):
  +0x00  u32 x4  全零
  +0x10  13B     name(ASCII, \0 填充)
  +0x1D  3B      地址空间标记  ← 新发现
  +0x20  u32     size
  +0x24  u32     offset
  +0x28  u32     flags
  +0x2C  32B     SHA-256(明文)
  +0x4C  12B     nonce/IV
  +0x58  u32     0
```

`+0x1D` 的 3 字节分成两个地址空间:
```
0x16xxxx 组(boot/loader*/storage/program/postboot*/eep_*/compress_pr)   ← 系统区
0x7Axxxx 组(lens_hist/lut*/osd*/music/wifi*/menu_save/grid/hm_*/dsp_*)  ← 数据区
```

**b) 数据起始偏移的 64KB 规律**:
```
grid_data   数据起始 mod 64K = 0x7A00,  长度 mod 64K = 0x8600
vkizu_data  同上
lut2_data   同上
0x7A00 + 0x8600 = 0x10000 (64KB)
lens_hist   数据起始 mod 64K = 0x0(唯一例外)
```

### 9.6 结论

**静态固件攻击已充分穷尽。** 加密为强算法(AES 级),per-partition nonce/子密钥,
密钥材料不在固件内(机型相关,推测在 SoC 安全区或 ROM)。

**数据不泄露任何可利用信息:**
- 非零部分熵 ≥ 7.988(无明文)
- nonce 无重复(无重用攻击)
- 已知明文(全零)因 nonce 各异不可互换

**后续观察需离开静态文件:**
1. **运行时内存观察** — 解密后的固件驻留 RAM
2. **硬件侧观察** — 需物理访问与专业设备
3. **协议层观察** — 记录设备与主机的交互(需相机在线)

> 说明:以上不是"没找到",而是"固件文件中不存在可利用的密码学信息"。
> 元数据(分区表 +0x2C 摘要)是设计上的**解密验证标尺**,可用于确认任何解密尝试。

## 10. 决定性发现:UPD = 加密 + 签名双重保护

### 10.1 UPD 头完整语义(已完全解析)

| 偏移 | 大小 | 含义 |
|---|---|---|
| `+0x000` | 4 | `"UPD\0"` magic (0x00445055) |
| `+0x004` | 4 | block size = 512 |
| `+0x008` | 4 | block size = 512 |
| `+0x00C` | 16 | 机型 ID(`MC8223X` / `MC8223`) |
| `+0x01C` | 4 | `0x02740274` |
| `+0x020` | 4 | `0x00010004` |
| `+0x024` | 4 | **版本/日期字段**(X=`0x02102019`, M=`0x02102018`) |
| `+0x02C` | 4 | 3 |
| `+0x034` | 4 | 3 |
| `+0x038` | 4 | 512 |
| `+0x03C` | 4 | image_data_size = 179,206,656 |
| `+0x040` | 4 | CRC32(数据区 `[0x200..末尾]`) |
| `+0x200` | 16 | `"panasonic"` 标识 + 填充 |
| **`+0x220`** | **64** | **ECDSA P-256 签名 (r‖s)** ← 关键发现 |
| `+0x2A0` | 512 | 第二个 UPD 记录(与 `0x0` **完全相同**,冗余备份) |

### 10.2 0x220 的 64 字节 = ECDSA P-256 签名

```
S5M2X: r = 0x6601F80A9B158E0D2ACCF8C082AF148910F4E9D31D19E9122444AAE70309C022
       s = 0x504E685692529ABB585542841200A75FD92E87A10A2EDD31484111DCE35EE1ED
S5M2 : r = 0x1AAC8FFDC7BA7EFD2A960E9AD6CAA7709C0FBECB8F1739CC264F4AEB82DF4558
       s = 0xECA69487786CC66BF762686BED7A9F4149C636F2380956E92E6F2385B8CD3B74
```

**验证依据**:
- `r`、`s` 均满足 `1 <= r,s < N`(N = P-256 曲线阶)
- S5M2X 的 `s <= N/2`(低 s 标准化,规范签名特征)
- 两机型**完全不同**(各自固件的签名)

**判定:ECDSA P-256 数字签名**,用于固件完整性/来源验证。

### 10.3 ⚠️ 决定性含义:修改镜像不可行

```
AES 加密          → 阻止读取/分析代码
ECDSA P-256 签名  → 阻止篡改固件
```

**即使获得 AES 明文并修改 `program`,签名校验也会拒绝该镜像。**
ECDSA 私钥在厂商侧,不可获取 → **镜像完整性由签名保障,修改后的镜像无法通过校验。**

### 10.4 这轮排除的分析路径(全部无效,但结论明确)

| 分析路径 | 结果 |
|---|---|
| keystream 复用搜索 | ❌ 每个探针只在自己位置 |
| 数据区对齐比较(修正取值错误后) | ❌ 256/256 全不同 |
| 两机型 keystream 差分 | ❌ 全随机 |
| 系统性 nonce/key 派生(分区名×tail3×机型×布局×字节序) | ❌ 全未命中 |
| **字典攻击**(固件全部短字符串作 key) | ❌ 10 万+ 组合未命中 |
| **常见明文模式猜测**(全0/全FF/递增/重复块)用摘要验证 | ❌ 仅命中"全零" |
| **UPD 头 64 字节作密钥** | ❌ 它是签名,非密钥 |
| keystream 随机性检测 | **熵 7.9995、卡方 274.5、无自相关、块唯一率 1.0** → 强加密确证 |

### 10.5 新增结构发现

- **`menu_save` 逻辑内容 = 全 `0xFF`**(摘要 = SHA-256(全FF)),而镜像全零
  → 证明摘要描述「应有内容」而非镜像字节
- **分区项 `name` 后 3 字节 = flash 地址空间标记**:
  `0x16xxxx`(系统区) / `0x7Axxxx`(数据区)
- **数据起始偏移规律**:`N×0x10000 + 0x7A00`,`0x7A00 + 0x8600 = 64KB`

### 10.6 最终结论

**静态分析已到边界**(AES 强加密 + ECDSA 签名)。
继续在固件文件上投入不会产出结果 —— 这不是"没找到",是**文件内不存在可利用信息**。

**协议层可在不修改固件的前提下进行观察**(不涉及加密与签名的处理)。

## 11. 老平台解剖 + 明文分区目录表(新发现)

### 11.1 老平台的架构(Linux)

S1/S1H/S5 分区表含 Linux 系统组件:
```
zimage(2.6MB 内核) dtb(设备树) rootfs1/rootfs2(文件系统)
zboot apu0_code/data_i/e ipu_rc_nr_code/data  mult_fpga(S1H) / lns_fpga(S1)
```
**但全部加密**(熵 8.000,解压测试全部失败),包括 `zimage`/`rootfs`。

### 11.2 ★ 新发现:loader2/loader3 内含明文分区目录表

`loader2` **开头是明文结构**(4 字节头 + N × 92 字节项):

```
S1H loader2 (38912 B):
  #  name          A(flash地址)  size        B           flg  hash[:8]
  0  nr_data       0x0499BC00      262,144  0x04E60000    3   e235e388...
  1  nr_code       0x049DBC00       65,536  0x04EA0000    3   2553aa1d...
  2  hm_c_prog     0x049EBC00       65,536  0x04EC0000    3   06e44fbb...
  ...
  10 hr_c_ddr      0x0568BC00      262,144  0x05B80000    3   dda4ddd0...

  → 全部 11 项的 size 与 hash 与主分区表完全一致
```

**项结构(92 字节)**:
```
+0x00  12B   name
+0x0C  u32   A(flash 地址)
+0x10  u32   size
+0x14  u32   B(另一地址,可能是 RAM 加载地址)
+0x18  u32   flags(=3)
+0x1C  32B   SHA-256(明文内容哈希,与主分区表相同)
```

**含义**:协处理器程序(nr_/hm_/hr_)的加载表,**明文存储**。

### 11.3 镜像是「真 flash 重排」后的包

对比 `loader2.A`(flash 地址)与分区表 `off`(镜像位置):

| 分区 | loader2 A | 镜像 off | 差 |
|---|---|---|---|
| nr_data | 0x0499BC00 | 0x04E60000 | 0x4C4400 |
| hm_c_prog | 0x049EBC00 | 0x04EC0000 | 0x4D4400 |
| hm_d_ddr | 0x04D3BC00 | 0x05220000 | 0x4E4400 |
| hr_c_ddr | 0x0568BC00 | 0x05B80000 | 0x4F4400 |

**差值阶梯式递增,步进 0x10000(64KB)** →
1. 镜像内的**紧密排列**是从"64KB 对齐的 flash 分配"重排而来
2. 再次印证 **64KB 块结构**

### 11.4 结论

**固件有多层完整性元数据**(全部明文):
```
主分区表(58 项,SHA-256 + nonce + flags)
loader2/loader3 目录表(A/B 地址 + SHA-256)
UPD 头 CRC32
ECDSA P-256 签名
```

**但依然没有密钥材料。** 所有分区数据(含 `zimage`/`rootfs`)均加密,
明文只存在于**元数据层**。静态分析仍不暴露明文。

**新增可复现脚本**:`analysis/body/old_platform.py`, `old_decompress.py`,
`loader2_dir2.py`, `addr_check.py`, `gap_analysis.py`

## 12. 盲点终检与自我纠正(加密破解的最终结论)

### 12.1 三个此前未查的盲点(逐一排除)

| 盲点 | 检查结果 |
|---|---|
| 分区项 `+0x00..+0x10` 的 16 字节 | **基本全零**(53 项中仅 `loader1` 非零,内容是镜像元数据:总大小 `0x056CBC00` + 分区数 `0x35`=53,非密钥)|
| `loader2` 剩余区(目录表之后 37,896 B) | **也是加密数据**(见 12.2)|
| `loader3` 全部(49,152 B) | **也是加密数据** |
| UPD 头 `+0x00..+0x80` 全部字段 | 均为已知元数据,无密钥材料 |

### 12.2 ★ 一处自我纠正:小窗口熵会误导

分析 `loader2` 剩余区时,按 256 字节窗口统计得到熵 **7.0~7.3**,
一度误判为「压缩而非加密」。**对整块重算后熵实为 7.9954**,与已知加密数据一致:

| 指标 | loader2 剩余区 | program(已知加密) | 随机理论值 |
|---|---|---|---|
| 整体熵 | **7.9954** | 7.9973 | 8.0 |
| 卡方(256 桶) | 240.0 | 241.9 | ≈255 |
| 零字节比例 | 0.3853% | 0.382% | 0.3906% |
| 相邻字节相同率 | 0.3800% | 0.377% | 0.3906% |
| 4 字节对齐零 u32 | 0.02% | — | ≈0 |

**结论:该区域是加密数据,不存在压缩流或明文结构。**
小窗口(几百字节)的熵波动大,不能作为格式判定依据 —— 此点已写入脚本注释以免后人再踩。

### 12.3 尝试过的解压路径(全部失败)

对 `loader1`/`loader2`/`loader3` 的多个起点(`0x0`/`0x4`/`0x3F8`/`0x400`/`0x1000`):
`zlib`(wbits 15/-15/31/47)、`gzip`、`lzma`(AUTO/XZ/ALONE/RAW-LZMA1/RAW-LZMA2)、`bzip2`、`zstd`
—— **无一成功**。

### 12.4 最终结论

**固件静态分析路径已穷尽,确定无可行方案。** 依据:

```
1. 所有数据分区加密     —— 含 loader / zimage / rootfs,无一例外
2. 明文仅存在于元数据层 —— 分区表 / loader2 目录表 / UPD 头 / ECDSA 签名
3. 密钥非简单派生       —— 6 机型 × 多 keystream 样本,17,496 组合全败
4. 每机型·每分区独立密钥 —— 同 nonce、同 size、同明文的密文跨机型 100% 不同
5. 即使破解成功         —— 仍无法通过 ECDSA P-256 签名校验
```

**这不是"未找到",而是经过多机型、多样本、多算法的反复验证。**

### 12.5 唯一可能突破的方向(均需离开静态文件)

1. **运行时内存提取** — 相机运行时固件以明文驻留 RAM(需相机在线 + 读内存通道)
2. **UART / JTAG** — 老平台为嵌入式 Linux,调试口未关闭的可能性较高;引导阶段可获取解密后镜像或读取 OTP/ROM 密钥(需拆机)
3. **USB/PTP 协议层** — 不触及固件,直接下发命令(需相机在线)

**新增可复现脚本**:`analysis/body/blind_spots.py`, `loader_decompress.py`, `loader_struct.py`
