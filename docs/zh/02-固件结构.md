## 2. 文件头

```text
偏移      字段
0x00  u32  magic        = 0x00445055  "UPD\0"
0x04  u32  block_size   = 512
0x08  u32  block_size2  = 512
0x0C  16B  model_id     = "MC8223X" + \0 填充
0x200     "panasonic" 标识
0x3C  u32  image_data_size = 179,206,656 (0x0AAE7A00)  镜像数据总大小
0x40  u32  checksum     = 0x752E308D                  头部校验
0x2DC     分区表起始
0x80000   数据分区起始
```

**验证**:`image_data_size = 179,206,656`,而 `boot` 分区位于 `179,201,024`、大小 `5,632`,
末端恰好 `179,206,656` —— 完全吻合,证明该字段与分区表自洽。

## 3. 分区表项结构(92 字节)

```text
偏移    字段
+0x00  u32   镜像数据总大小(各项相同)
+0x04  u32   boot 分区大小(仅 boot 项有效)
+0x08  u32   boot 分区偏移(仅 boot 项有效)
+0x0C  u32   校验类型
+0x10  16B   name(ASCII,\0 填充,超过 16 字节会截断,如 "compress_pr")
+0x20  u32   分区大小
+0x24  u32   分区偏移
+0x28  u32   标志:2 = 明文/空,3 = 加密
+0x2C  32B   摘要(MD5/SHA-256)
```

**表尾判定**:`flags` 只允许 `2`/`3`;一旦出现其他值即为数据区,必须停止解析。
(否则会把密文误当成分区项,产生数百条垃圾记录。)

**字段关系验证**:
```text
program       off 0x00080000 + size 0x02CC0000 = 0x02D40000
compress_pr   off 0x02D40000                  ← 正好相接 ✓
```
全部 58 项连续性检验通过,相邻分区 `gap = 0`。

## 5. 加密 —— 当前的核心障碍

| flags | 分区数 | 平均熵 | 判定 |
|---|---|---|---|
| `3` | 32 | 5.94 | **加密**(`program` `compress_pr` `postboot*` `osd*` `music` 等) |
| `2` | 9 | 1.15 | 明文/空(`menu_save` `lut_data` `wifi_info` 全零) |

判断依据:**熵恒为 8.00 整数**。压缩算法(zlib/lzma/zstd 极限压缩)通常停在 7.6~7.9,
且不可能在数万字节的窗口上稳定维持 8.000。这是**加密**的典型特征。

可分析的明文/低熵分区:
- `eep_fix`(2.73)、`hr_d_prog`(3.37)、`grid_data`(4.42)、`vkizu_data`(1.71)、`lut2_data`(1.54)
- `boot`(明文,5,632 B)—— **解密逻辑可能位于此处**

## 6. 对配置结构的观察

### 功能配置的存储方式

`menu_save` 在固件包内是**全零** —— 说明菜单/功能开关是**运行时写入**的,
固件镜像本身不含配置数据。配置的判定逻辑位于 `program`,
而 `program` 为密文,故该逻辑在静态分析下不可见。

`lut_data` 全零、`lut2_data` 低熵 —— 付费 LUT 数据独立存放,固件包内不含。

### 分析路径比较

| 路径 | 可行性 | 说明 |
|---|---|---|
| A. 取得 `program` 明文 | 中 | 需先在 `boot`/`loader1` 中定位解密算法与密钥 |
| B. **协议层(PTP)观察** | **高** | 不涉及固件解密,相机已切到 tether 模式,PID `2382` |
| C. 修改镜像 | 极低 | 受签名校验(`+0x2C` 32 字节摘要)约束 |

**路径 B 优先** —— 不涉及密钥与解密,可直接观察设备行为;
A 作为深入方向并行推进。C 仅记录可行性,受签名保障所限。

## 7. 校验机制 —— `+0x2C` 是 SHA-256(已确定)

用明文分区反推,确认 **`+0x2C` 的 32 字节摘要 = SHA-256**:

| 分区 | 存储摘要 | 验证方式 | 结果 |
|---|---|---|---|
| `lut_data` | `7b15c3f99be0c5f9...` | `SHA-256(镜像原始字节)` | ✅ **完全匹配** |
| `boot` | `e3b0c44298fc1c14...` | `SHA-256(去尾部 0xFF)` = `SHA-256(空)` | ✅ **匹配** |
| `menu_save` | `3b874d3ba46c638f...` | 全零 262,144 B,各候选算法均不匹配 | ⚠️ |
| `eep_act_a` | `3bdcb4d0d03318c6...` | 全零 512 B,各候选算法均不匹配 | ⚠️ |

已排除的候选:MD5 / SHA-1 / CRC32 / `SHA-256(raw)` / `rstrip(0x00)` / 非零字节拼接。

### 关键推论(解密正确性的验证标尺)

`boot` 全为 `0xFF`(flash 擦除态)时,摘要退化为 `SHA-256(空)`:
说明**摘要是对"有效内容"计算的,而非镜像中的原始字节**。

由此推断:**加密分区的摘要 = `SHA-256(解密后内容)`**。

> 这意味着每次尝试解密后,只要计算 `SHA-256` 与分区表中的 `+0x2C` 比对,
> 即可**确定性地验证解密是否正确** —— 无需猜测,有明确的判定依据。
> 这是后续解密分析工作的核心工具。

`menu_save` / `eep_act_a` 的摘要不匹配任何明文候选,
推测其摘要是"出厂默认内容"或解密后内容的哈希,待进一步确认。
