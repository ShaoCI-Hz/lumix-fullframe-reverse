# 镜头固件 —— 完全明文,含符号表(重大发现)

> **核心发现**:Panasonic **镜头固件未加密**,且保留完整函数/变量符号表。
> 这与机身固件(强加密 + ECDSA 签名)形成鲜明对比,是整条逆向路线中**信息量最大的资源**。

## 4. ★ 是 ARM Cortex-M 代码

`CABRIOLET` 附近即为**标准 ARM Thumb 指令**:

```text
0x068FD8  e1 ee 10 0a | 70 47         ← 70 47 = BX LR(函数返回)
0x068FE8  ff f7 d4 ff | af f3 00 80   ← ff f7 = BL(函数调用)
0x069018  80 b5 ... 02 bd             ← 80 b5 = PUSH {R7,LR};02 bd = POP {R7,PC}
0x069038  43 41 42 52 49 4f 4c 45 54  ← "CABRIOLET\0\x01A"
```

**判定:镜头 MCU 为 ARM Cortex-M,固件可直接反汇编(IDAPython/Ghidra,Thumb 模式)。**

## 5. 意义与可行动方向

### 5.1 直接价值:镜头控制协议可完整逆向

符号表 + ARM 代码 = 可还原 OIS / 光圈 / 对焦 / 变焦的完整控制算法与寄存器定义。

### 5.2 战略价值:松下并非"全部加密"

机身固件 = **AES 强加密 + ECDSA 签名**;镜头固件 = **完全明文 + 保留符号**。
说明加密是**针对机身的有意选择**,且镜头的"更新文件"格式是**另一套体系**。

### 5.3 ★ 一处结构性观察:相机必须能处理明文固件

相机要把 `.plf` 通过卡口下发给镜头,说明**相机的固件处理逻辑存在处理明文格式的分支**。

由此可得到的技术认识:
1. 相机固件更新器支持多种容器格式(`UPD` 加密 / `LENS-UPDATE-FILE` 明文)
2. 相机的固件处理路径中,存在一条面向明文格式的分支
3. L 卡口总线上的 `.plf` 传输为明文,可用逻辑分析仪记录

### 5.4 其他样本

L 卡口镜头均可下载,命名规律:
```text
https://panasonic.jp/support/share2/eww/com/dsc/ff/zip/<型号>V<版本>.zip
例:S-R24105V020.zip / S-E2470V010.zip / S-S85V010.zip ...
内部文件名如 4001V020.plf(4001 = 镜头内部型号码)
```
多镜头固件差分可定位"共享模板"与"型号补丁",快速通吃全部镜头。

## 9. ARM Cortex-M 反汇编分析(capstone)

### 9.1 容器结构修正:`EOH` = End Of **Header**(不是 End Of File)

```text
0x000000  "LENS-UPDATE-FILE-SOF:"      ← Start Of File
0x000015  头部字段  (00 02 | 07 e9 | 03 07 00 01 | 00 03 ...)
0x000058  "LENS-UPDATE-FILE-EOH:"      ← End Of HEADER
0x000070  "HDFLSPPSLFDI" / "IDFLSPPSLF00"   ← 段标记
0x000084  0x00000200 = 512             ← 块大小
+0x29     00 6D + 8 字节高熵数据         ← 疑似校验/签名
```

**因此 `.plf` = SOF 头 + 段表 + 数据段**,数据段有独立布局 —— 这解释了
为何直接从任意偏移反汇编会错位。

### 9.2 确认为完整 ARM Cortex-M 程序(capstone 统计)

| 特征 | 数量 |
|---|---|
| `PUSH` 序言模式 | **2,490** |
| `BX LR`(`70 47`,函数返回) | **1,311** |
| `BL` 调用模式(`f0-f7 f8-ff`) | **1,078** |

反汇编样例(`0x049800`,指令对齐正确):

```asm
0x04980E  push   {r2, r3, r4, lr}     ; 函数序言
0x049810  mov    r4, r0
0x049816  cmp    r4, #0
0x049818  beq    #0x49828
0x049820  bl     #0x60bd8             ; 函数调用
0x049828  pop    {r0, r1, r4, pc}     ; 函数尾声
```

### 9.3 代码段分布(按指令密度)

```text
0x02D000(0.56)  0x031000(0.73)  0x03B000(0.71)  0x040000(0.51)
0x042000(0.58)  0x045000(0.79)  0x04E000(0.81)  0x057000(0.71)  0x062000(0.79)
```

代码被拆成多个段,与数据段交替 —— 典型的分段链接布局。

### 9.4 未找到典型向量表

在文件内未发现 Cortex-M 复位向量表(候选均落在数据区),
说明 **代码在文件中的偏移 ≠ 加载地址**,`.plf` 是**打包容器**,
需要先解析段表(把段搬到加载地址)才能完整反汇编。

### 9.5 复现

```bash
python analysis/lens/lens_disasm.py         # 代码区定位(Thumb 特征密度)
python analysis/lens/lens_disasm2.py        # 向量表/代码分区/字符串引用
python analysis/lens/lens_header_struct.py  # 头部与段结构
# 完整反汇编输出:analysis/lens/lens_disasm_output.txt
```

### 9.6 结论

镜头固件是**完整的、可反汇编的 ARM Cortex-M 程序**,已具备符号表 + 代码段定位。

**下一步只需解析段表**(把段映射到加载地址),即可用 Ghidra/IDA 做完整的
函数级还原。这是所有相机固件样本中可分析性最高的一个。

## 10. 段表解析尝试(结论:需先解出段布局)

### 10.1 容器内的厂商标记

```text
0x006D  "PSLFDH"          ← 头部字段后的标记
0x0078  "HDFLSPPSLFDI"     ← 段标记 1
0x009A  "IDFLSPPSLF"       ← 段标记 2(后接 "00")
0x00CF  "QIPL"
0x02D7  "PHUL"
```

另有 `0x84: 512`(块大小)、`0xB4: 0x2000` 等数值;头部含 8 字节高熵数据
(`+0x2B..+0x33`),疑为校验或签名。

### 10.2 未找到可用向量表

改进搜索(要求 word0 像栈指针、word1..N 像 Thumb 地址)得到 49 个候选,
但**全部落在数据区**(如 `SP=0x00404040`),无一是真实复位向量表。

**推论**:代码在文件中的偏移 **≠** 加载地址,`.plf` 是**打包容器**,
必须解析段布局才能重建可加载镜像。

### 10.3 线性扫描不可靠(实测)

```text
BL/BLX 指令        5,688 条
目标落在文件内      89.1%      ← 看似合理
目标落在高密度代码块 25.1%      ← 实际很低
```

从任意偏移做线性反汇编会产生大量误报(数据段被误判为指令),
例如 `0x00FD00` 处的"反汇编"出现 `svc #0xb2`、不合理的 `ldm` 序列等。

**因此:必须先把代码段与数据段分离开,才能获得可信的函数级反汇编。**


## 11. ★ 段表的替代路径:种子 + 前向扫描(已成功)

**关键认识:该方法不依赖段表。** 用"函数序言"作种子 + 递归下降,直接得到可信函数集合。

### 11.1 方法

线性扫描不可靠(数据区被误判为指令),改用:

1. **序言种子**:Thumb `PUSH {r0-r7,lr}`(`0xB5xx`)与 `PUSH.W`(`e92d ..`)——
   这类字节序列在数据中几乎不可能自然出现
2. 从种子**反汇编到函数结尾**(`pop {..,pc}` 或 `bx lr`)
3. 收集 **BL 目标**作为候选函数入口
4. **交叉验证**:`BL 目标 ∩ 序言` = 高置信入口

### 11.2 实测结果

```text
序言种子                  1,147 个
  其中可完整反汇编          694 个 (60.2%)
BL 目标(被调用点)        2,532 个
  反汇编成功率            81.5%   ← 高于序言种子
高置信函数入口             101 个  ← BL 目标 ∩ 序言(双重验证)
可信函数覆盖              31.2% 的文件(155,366 / 497,494 字节)
```

### 11.3 ⚠️ 原结论已撤回:加载地址 = 文件偏移(**未获证明**)

> **勘误(经独立子代理复核后添加)**
>
> 本节初版声称"BL 目标 99.9% 落在函数区间内 ⇒ 加载地址 = 文件偏移"。
> **该推理不成立,现予撤回。**

**撤回理由(已用代码复现验证):**

1. **"函数区间"的并集覆盖了 98.59% 的文件**

```text
   文件大小    497,494 字节
   区间并集    490,476 字节 = 98.59%
   区间并集 = [0x001B6A, 0x079756)   ← 从第一个种子一直铺到文件末尾
```

   因为区间构造为 `[(se[i], se[i+1]) ... (se[-1], n)]`,
   **任何大于 0x001B6A 的目标都会"落在区间内"** —— 这个测试几乎没有区分能力。

2. **"BL 目标"里混入了普通 `B` 分支**

   收集代码用的是 `ins.mnemonic in ('bl', 'b', 'blx')`,**包含 `b`**:

```text
   纯 BL/BLX 目标 : 5,688
   普通 B   目标 : 5,116   ← 47%,不应计入"函数调用"
   合计           : 10,804
```

   而 `B` 是函数内跳转:**77% 的 B 目标距其区间起点 < 0x400**,
   计入后必然把命中率推高 —— 这是自我实现的测量。

3. **严格标准下的真实数字**

   | 标准 | 落在高密度代码块 |
   |---|---|
   | 仅 BL/BLX | **22.4%** |
   | BL+B(原用法)| 17.1% |
   | §10.3 的诚实测量 | 25.1% |

   **原 §10.3 的 25.1% 才是有效数字;§11.3 用更弱的测试"升级"了结论,这不是新证据。**

4. **base 测试本身不具决定性**:base=0 只精确命中 2.3% 的目标,
   这与"种子集不完整"下的预期接近,**无法据以确认 load==offset**。

**修正后的准确表述:**

> **加载地址是否等于文件偏移,目前仍未确定。** 它既未被证明,也未被否证。
> 需要解析段表(§10)或做段内地址一致性检验才能判定。

**这直接影响可用性结论**:§11.6 曾说"可载入 Ghidra/IDA" ——
在加载地址未确定前,**该说法应降级为"需要先在 Ghidra 中试配基址"。**

### 11.4 调用链验证(自洽)

```text
0x02C2D0  push {r4,r5,r6,lr}     ← 序言
0x02C2DA  bl   #0x2C3CC          ← 调用
```

### 11.5 ⚠️ 方法命名勘误:这不是"递归下降"

> 本节初版把该方法称为"递归下降反汇编",**该称呼不准确**。
>
> 实际实现(`analysis/lens/lens_recursive.py` 的 `follow_targets()`)是:
> **从每个种子前向线性解码到第一个 return,并"收集"遇到的跳转目标** ——
> 它**从不下降进这些目标**。正确名称是
> **"种子 + 前向线性扫描"(seed-based linear sweep)**,而非递归下降。
>
> 同时:种子判定 `d[o+1] == 0xB5` 是 ~1/256 的字节谓词。
> 在 ~248K 个偶数偏移上,期望偶然命中约 **970** 次 —— 实测 **1,147** 次。
> 二者接近,**因此这 1,147 个种子中有相当部分可能是数据巧合**,
> 而"几乎不可能在数据中自然出现"的原表述**过于乐观**。
> 未做 0xB5 频率基准(null model)检验,这是该方法的已知弱点。

## 12. 符号区性质判定:是「变量名表」而非「函数符号表」

对 §3 提到的 578 个符号做了格式解剖,**结论修正**:

### 12.1 实际结构

```hex

005420  74 00 00 00 00 00 00 00 ...                        |t...............|

0x5413  "OISPwAdjAdjSet"
```


| 假设 | 命中率 |
|---|---|
| 名字后 4 字节是 Thumb 地址 | **5 / 575** |
| 名字前 4 字节是 Thumb 地址 | 67 / 575(均为跨字符串边界的误报)|

→ **该表不含地址**,因此**不能**直接映射到函数入口。

### 12.3 但仍然很有价值:功能语义可读

变量名按模块成组出现,直接暴露子系统划分:

## 13. ★ 间接映射实测:变量表是「纯调试元数据」

按 §12.4 的思路做了两轮实测,**得到的结论比预期更有价值**。

### 13.1 变量名没有任何代码引用

```text
变量名(0x4000-0x9000 区)        388 个
被 literal 池引用的                1 个   ← 唯一命中的是字符串碎片误报
```

### 13.2 排除了一个方法错误

此前检测"名字旁 4 字节是否像地址"时要求 *地址 < 文件大小* —— 这是**错的**:
变量位于 **RAM**,其地址应在 `0x2000xxxx` 段,**本就不在文件内**。

改用 RAM 地址范围重新检测:

```text
名字后 4 字节 Top: 0x00000000 x106,其余为字符串残片 —— 无地址字段
名字前 4 字节 Top: 0x00000000 x78,其余为字符串残片 —— 无地址字段
```

### 13.3 但代码确实大量引用 RAM

```text
全文件 RAM 地址引用(按 1KB 块聚合):166 个块
  0x20002000 x458   0x20004400 x273   0x2000D000 x189
  0x20000000 x177   0x2001D000 x170   0x2000F800 x122
  ...
```

**代码只操作 RAM 地址,完全不引用变量名字符串。**

### 13.4 结论:变量表服务于「运行时调试通道」

变量表**不含地址、不被代码引用**,却又保留了完整的变量名与类型 ——
**唯一合理的解释是:它供"按名字访问变量"的调试接口使用**。

旁证(该表中确实存在调试类变量):

```text
DbgMode        DrvMode       LogData1..8       ErrLSB
LockErr        ChkGyro       Adj_Pos           AvMaxVlF
```

**这对本项目是有意义的发现:**

1. **镜头 MCU 具备运行时调试能力** —— 可通过名字读写内部变量
2. `DbgMode` 的存在说明**调试模式可由外部进入**
3. 若该调试通道在**正常使用时仍可用**,则为观察镜头内部状态提供了入口
4. 这条路径**绕开了镜头固件的静态分析难点**,直接进入动态观察

### 13.7 ⚠️ 勘误与自我修正(独立子代理复核后添加)

> 独立复核对本节的判读提出了**合理的质疑**,记录如下。

**质疑点:"把 1 个引用直接舍入为 0,再据此得出'调试元数据'的叙事"**

## 14. 容器头部结构:段/块描述表(非代码)

继续解剖 `.plf` 头部,确认它是**表结构**而非可执行代码。

### 14.1 头部布局

```text
0x0000  "LENS-UPDATE-FILE-SOF:"              (21 B)
0x0015  头部字段 00 02 | 07 e9 | 03 07 00 01 | 00 03 ...
0x0058  "LENS-UPDATE-FILE-EOH:"              (21 B) ← End Of HEADER
0x006D  "PSLFDH" + 01

0x009A  "IDFLSPPSLF00"

0x00B8  0x00000200 = 512
0x00B0+ 段/块描述表开始
```

### 14.2 判定为「表」而非「代码」的依据

**(a) 反汇编产出不合理的指令流。** 在 `0x00F0` 起多个对齐位置尝试 Thumb 解码,
得到的都是成串的无意义指令:

```text
0x00F0  4811  asrs r0, r1, #5
0x00F2  4901  lsls r1, r1, #5
0x00F4  540c  lsrs r4, r2, #0x11
0x00F8  4901  lsls r1, r1, #5
0x010A  70be  bkpt  #0x70        ← "数据被当作代码"的典型痕迹
```

**(b) `00 00 70 XX` 模式以 4 字节为步长规律出现:**

```text
出现位置步长: [4, 4, 4, 4, 14, 6, 4, 4, 4, 4, 10, 4]
```

按 u16 LE 从 `0x10E` 起解读,得到**严格递增且全部落在文件内**的地址:

| 偏移 | 字节 | u16 LE | 值 |
|---|---|---|---|
| 0x10E | `70 72` | 0x7270 | 29,296 |
| 0x112 | `70 90` | 0x9070 | 36,976 |
| 0x116 | `70 a2` | 0xa270 | 41,584 |
| 0x11A | `70 b0` | 0xb070 | 45,168 |

**(c) `0xB0..0x400` 中也存在接近文件末尾的地址:**

```text
0x0128  0x007070 =  28,784
0x014C  0x057270 = 356,976
0x0150  0x05EC70 = 388,208
0x016C  0x073270 = 471,664     ← 文件大小 0x79716 = 497,494
0x029C  0x025E70 = 155,248
```

### 14.3 这两个十字节值(512 / 8192)的意义

```text
0x0084 = 512    ← 与 §9.1 的"块大小"一致
0x00B4 = 8192
0x00B8 = 512
```

**512 反复出现**,与 UPD 容器(机身固件)的块大小相同 ——
说明 Panasonic 的固件容器在机身与镜头两侧**共享同一套块式布局约定**。

## 15. 段表求解尝试:两个负面结果(方法论记录)

用两种独立方法尝试定位数据区起点/段边界,**均未成功** ——
但两个负面结果都有记录价值。

### 15.1 跨样本对齐(4001/4002/4006)

取三个不同大小的样本,找"随文件大小变化"的头部字段:

```text
     off    4001V020(497,494)  4002V020(673,252)  4006V020(452,161)
  0x0018          459,753           1,379,305            265,449
  0x0084              512                 512                256
  0x00B4            8,192               8,192             40,960
```

**一个惊人的巧合**:

```text
4001:  37,741 + 459,753 = 497,494 = 文件大小  ✓
```

**但 4002 立刻反例**:`0x18 = 1,379,305 > 673,252 = 文件大小` ✗

**结论:`0x18` 不是"数据大小"**;单个样本的吻合是巧合。
另注:`0x84` 在 4006 上是 **256** 而非 512 —— 块大小**并非全局常量**。

### 15.2 熵扫描(更直接的方法,同样失败)

逐 4KB 块计算熵,**确实看到清晰分层**:

```text
0x000000 - 0x008000   H = 3.15 - 5.04    ← 低熵
0x009000 起            H = 6.28 - 6.89    ← 中高熵,稳定

且三样本在 0x2000-0x8000 熵几乎一致:
  3.79, 4.06, 3.93, 3.33, 3.15   ← 固定头部
```

初看像是"头部 + 数据区"的干净分层。**但实际内容检查推翻了它:**

| 偏移 | 实际内容 | 是否代码 |
|---|---|---|
| `0x8000`(4001)| `02 0a 02 0a 02 0a ...` 重复模式 | ❌ 数据表 |
| `0x9000`(4006)| `72 6b 46 53 74 6f 70 70 65 72` = `"rkFStopper"` | ❌ 字符串 |
| `0x8800..0x9200` | 函数序言(`0xB5xx` / `e92d`)数量 | **0 个** |

**最关键的反证:**

> 此前**已验证为真函数**的 `0x02C2D0`、`0x02C3CC`,落在熵 **3.9 - 4.9 的"低熵区"**。

**因此:熵无法可靠区分 code / data。**
字符串表与常量表的熵同样能达到 6.5+,而真正的代码可以落在低熵区。
**"熵高 = 代码"的直觉在这里是错的。**

### 15.3 方法论教训(与 §3 的既有规则呼应)

仓库 `docs/03` §12.2 早已确立一条规则:**熵不能单独作为格式判定依据**。
本节是这条规则在镜头固件上的**第二次应验**:

| 场合 | 误用 | 后果 |
|---|---|---|
| `docs/03`(机身)| 小窗口(256B/4KB)熵→"压缩而非加密" | 误判,改用 ≥64KB 纠正 |
| **本节(镜头)** | 中熵区 → 推测"数据/代码起始" | **误判,内容检查纠正** |

**正确做法**:熵只用于**粗筛**(排除全局强加密),
确定 code/data 边界必须靠**内容特征**(有效 Thumb 解码率、函数序言密度、字符串)。

## 16. 跨镜头固件对比:独立链接 + 变焦/定焦两套架构

### 16.1 ★ 关键发现:各镜头固件是独立链接的

取 6 个镜头固件,比较**函数序言的文件偏移**:

```text

```

| 比较层次 | 结果 |
|---|---|
| **偏移级**两两交集(Jaccard)| **≈ 0.002** |
| **偏移级** 6 样本共同序言 | **0 个** |
| **块级**(512 对齐,≥3 样本有序言)| **705 / 988 = 71.4%** |

**偏移级交集≈0 而块级共享 71.4%** —— 这强烈说明:

> **每个镜头固件都是从同一套源码「独立链接」出来的**

**推论**:不能用"相同文件偏移"来找跨型号的共享函数,

## 19. ★★ 找到加载基址(0x08000000)—— 修正 §11.3

§11.3 撤回"C 加载地址 = 文件偏移"后,加载地址一直悬置。
改用**内存映射段特征**重新求解,**这次得到了确切答案**。

### 19.1 完整的标准 Cortex-M 内存映射

统计全文件 4 字节值落在各地址段的数量:

| 地址段 | 含义 | 引用数 |
|---|---|---|
| `0x00000000-0x000FFFFF` | 低地址/别名 | 20,840 |
| `0x08000000-0x08FFFFFF` | **Flash** | **5,191** |
| `0x20000000-0x200FFFFF` | **SRAM** | **4,475** |
| `0x40000000-0x400FFFFF` | **APB/AHB 外设** | **572** |
| `0xE0000000-0xE00FFFFF` | **Cortex-M SCS(系统控制)** | **1,346** |

这四个段(Flash / SRAM / 外设 / SCS)正好构成**标准 ARM Cortex-M 内存映射**,
从内存布局角度**再次确证该固件是 Cortex-M 程序**(与 §9 结论一致)。

### 19.2 ★ 决定性证据:基址 = 0x08000000

Flash 段引用的地址范围是 `0x08000000 .. 0x080FFFF1`。
**检查减去基址后的落点:**

```text
0x08000000 → 偏移 0x000000: 4c 45 4e 53 2d 55 50 44 41 54 45 2d 46 49 4c 45
                            = "LENS-UPDATE-FILE"   ← 正是文件开头!
0x08000019 → 偏移 0x000019: 03 07 00 01 00 03 ...   ← 头部字段
0x0800001A → 偏移 0x00001A: 07 00 01 00 03 00 ...   ← 头部字段
```

**`0x08000000` 精确指向文件第 0 字节的 `"LENS-UPDATE-FILE"`** —— 这不是巧合。

**更直接的证据**:代码中真实存在把它当指针使用的指令:

```asm
0x0277D4  ldr  r1, [pc, #0x200]        ; 加载 0x08000000
          literal @0x0279D8 = 0x08000000
```

全文共 **585 条 `LDR literal` 加载 Flash 段地址**(典型的"取数据/表地址"模式)。

### 19.3 修正后的准确表述

| | 表述 |
|---|---|
| §11.3 初版(已撤回)| "加载地址 = 文件偏移" ❌ |
| **§19 修正** | **运行地址 = 文件偏移 + 0x08000000** ✅ |

即 `.plf` 的代码/数据在设备上运行于 `0x08000000` 起始的 Flash 空间,
文件偏移 `X` 对应运行地址 `0x08000000 + X`。

### 19.4 地址位分布:以数据指针为主

```text
Flash 段不同地址值 1,852 个:
  偶数(bit0=0,数据指针)      : 1,585   ← 多数
  奇数(bit0=1,Thumb 代码指针):   267
```

**以数据指针为主** —— 说明这些引用绝大多数指向**常量表/查找表/字符串**。
若存在函数指针表,应呈现大量奇数地址;实测奇数占比仅 14%,故**未发现函数指针表**。

### 19.5 未解释的部分:尾部超界地址

部分地址减去基址后**超出文件大小**:

```text
0x080F7C48 → 偏移 0x0F7C48   (文件仅 0x79756)
0x080FF002 → 偏移 0x0FF002
0x080FFFF1 → 偏移 0x0FFFF1
```

**最可能的解释:`.plf` 不含完整 Flash 镜像**,只包含需更新的部分;
运行时 Flash 的其余区域(如初始化模板、BSS 初值)不在文件内。
倾向此解,因为超界地址成片出现在 `0x080F7xxx` / `0x080FFxxx`,
符合"文件只覆盖 Flash 低地址部分"的特征。

1. **解决了 §10 / §11.3 一直悬置的加载地址问题**(此前两个方法均失败)
2. **可直接在 Ghidra/IDA 中以 `0x08000000` 为基址加载 `4001V020.plf`**,

## 20. 中断向量表不在 `.plf` 中(证实部分更新镜像)

有了基址 `0x08000000` 后,向量表搜索终于有了**精确条件**,于是重做 §10.2 失败的尝试。

### 20.1 搜索条件(基于 Cortex-M 规范)

一个真实的 Cortex-M 向量表首两项必须是:

```text
word[0] = 初始栈指针  → 必须落在 SRAM 段 0x20000000-0x2003FFFF
word[1] = 复位向量    → 必须落在 Flash 段,且 bit0 = 1(Thumb 状态)
```

### 20.2 结果:0 命中

```text
严格条件(word0∈SRAM, word1∈Flash|1, 且后续 7/8 项也得体): 0 个
放宽条件(仅要求 word0∈SRAM 且 word1∈Flash|1)           : 0 个
```

**文件里根本不存在"SRAM 地址紧邻 Flash|1 地址"的字节组合。**

### 20.3 结论:`.plf` 是部分更新镜像

这**独立证实了 §19.5 的推断**(当时只是推测):

> `.plf` **不包含完整的 Flash 镜像**,因此**不含运行时的中断向量表**。

**旁证与解释:**

- 文件偏移 `0` 处是 `"LENS-UPDATE-FILE-SOF:"` 字符串
- 而 `0x08000000` **恰好**指向它(§19.2)
- 即:**`.plf` 的第 1 字节 = Flash 的 `0x08000000`**
- 但向量表是**运行时结构**,位于更新镜像**不覆盖**的区域

**因此**:镜头 MCU 的 Flash 布局应为

```text
0x08000000  ┌─────────────────────────────┐
            │ ...(不在 .plf 内,含向量表?) │  ← 出厂引导区/基础固件
            ├─────────────────────────────┤
            │ .plf 覆盖区(含 SOF 头+代码)│  ← 本文件
            └─────────────────────────────┘
```

### 20.4 SRAM 引用分布(附带收获)

```text
SRAM 段引用总数: 3,572
  0x20000000 段: 2,180
  0x20010000 段:   786
  0x20020000 段:   400
  0x20030000 段:   206
```

**SRAM 使用跨越 4 个 64KB 块(0x20000000-0x2003FFFF ≈ 256KB)** ——
与 §13.3 的 166 个 1KB 块统计一致,说明该 MCU 的 SRAM 规模在 256KB 量级。

## 22. ★ 严格标准重建:种子问题被定量证实(85.5% 是数据巧合)

### 22.1 严格标准(双重验证)

```text
→ 即 85.5% 的宽松种子是数据巧合
```

**这定量证实了独立复核 agent 在 §11.5 提出的质疑**

### 22.3 真正的递归下降(迭代扩展)


**收敛意义重大**:工作集从 133 个入口开始、扩展 12 个后**完全闭合**,

> **`push {..,lr}` 不是完备的函数入口判定。**

## 23. ★★ 自建可达性递归下降:覆盖率 2.3% → 36.6%

**本轮不依赖外部工具,直接用可达性方法复现了它的核心机制。**

### 23.1 方法:放弃模式匹配,改用可达性

| | §22 严格版 | **§23 可达性版** |
|---|---|---|
| 入口判据 | **必须有序言**(模式匹配)| **只要是 BL/BLX 目标**(不再要求序言)|

## 24. 函数边界修正:三种方法的权衡已测量清楚

执行 §23.7 的方向 1(修正边界),并测出三种方法的**精度/召回权衡**。

### 24.1 修正 1:函数内扫描(分支不跨函数)

把分支跟随限制在**距入口 ±8KB** 内,且**分支目标不重新开函数**:

```text

规模均值                      : 148.3 指令
规模最大                      : 3,255 指令   ← 仍不合理
唯一覆盖                      : 14,644 指令 = 5.9%
调用图自洽性                  : 90/1747 = 5.2%
```

**边界精度改善**(中位数 28 与 §22 一致),但**覆盖率降到 5.9%**
—— 因为只从 133 个种子出发,不做全局可达性。

### 24.2 修正 2:融合(全部 BL 目标作入口 + 函数内扫描)

```text
入口候选(全部 BL 目标)      : 2,848
有效函数(≥3 指令)          : 2,726
唯一覆盖                     : 67,888 指令 = 27.3% 文件
规模中位数                   : 88 指令
规模均值                     : 189.1
规模最大                     : 2,469 指令
★ 重叠率                     : 50,814 / 67,888 = 74.8%
调用图自洽性                 : 34,105/34,941 = 97.6%
```

**★ 74.8% 的重叠率是致命信号** —— 说明**入口集质量差**:
2,848 个全文件扫描得到的 BL 目标中,**只有 133 个自身有序言**,
余下 2,715 个包含大量**数据区误检的"伪 BL"**。
从伪入口出发扫描,必然与其他函数大面积重叠。

**同时"规模最大 2,469 指令"仍未消除** —— 即使把分支跨度收紧到 1KB。

### 24.3 ★ 三种方法的权衡(本轮的核心产出)

| 方法 | 入口来源 | 精度 | 召回 | 结论 |
|---|---|---|---|---|
| **§22 严格** | BL 目标 ∩ 序言 | **高**(中位数 28,无异常) | **低**(133 函数 / 2.3%) | 高精度低召回 |
| **§23 可达性** | 种子 + 控制流可达 | 低(边界错,2469 指令) | **高**(36.6%) | 高召回低精度 |
| **§24 融合** | 全文件 BL 目标 | **低**(重叠 74.8%) | 中(27.3%) | 入口质量差,双向受损 |

**这正是"精度 vs 召回"的经典权衡**,而且本轮把它**量化**了:

- **要达到高精度**,必须用**强判据**(序言)→ 但序言不完备(叶子函数无 push)
- **要达到高召回**,必须放宽判据 → 但数据区会混入伪入口(重叠率飙升)
- **纯可达性(§23)** 是在**已知代码流**中扩展,不引入伪入口,
  但**边界判定**需要额外的函数结束条件

### 24.4 结论:正确方向是"代码流内收集,而非全文件扫描"

对比 §23 与 §24.2 的入口来源:

| | §23 | §24.2 |
|---|---|---|
| BL 目标从哪来 | **从可达代码流中遇到的** | **全文件扫描所有字节对** |
| 结果 | 覆盖 36.6%,call 边 98,360 | 重叠 74.8%,伪入口多 |

**§23 的做法是对的**:只在**已确认为代码的位置**收集 BL,
天然排除数据区的伪目标。§24.2 的全文件扫描则引入了污染。

**因此后续应:**

1. **入口 = §23 可达代码流中的 BL 目标**(而非全文件扫描)
2. **边界 = 用"返回地址栈"判定**(遇到 `pop pc` / `bx lr` 且分支工作集已空)
   —— 这是编译器生成的函数应有的结构
3. **放弃"全文件扫描 BL"这一路径**(已证明会污染入口集)

**(a) Ghidra 的盲区 → 我们的价值。**

它们**不在这 578 项之内**,且位于**代码区**而非头部。
它是在用 Ghidra 交叉核对字符串引用时(§27)发现的:
这个固件里几乎没有字符串被指令直接引用,
但代码区里一段连续的名字被证实是一张**定长表项的资源表**。

### 28.2 这张表

表项步长为 **12 字节**(名字 + NUL,零填充),22 项资源加 2 个信号量,共 288 字节:

| 类别 | 数量 | 名称 |
|---|---|---|
| **任务**(`_TSK`)| 9 | `INITIAL_TSK` `DATA_LATCH_TSK` `TRANS_TSK` `EXP1_TSK` `EXP2_TSK` `BLCOM_TSK` **`CMD_TSK`** `USER_TSK` `OIS_TSK` |
| **信号量**(`SEM_`)| 2 | `SEM_MS_SUBFI` `SEM_MS_SUBO` |
| **标志**(`_FLG`)| 7 | `USER_FLG` **`UART_FLG`** `OIS_FLG` `EXP1_FLG` `EXP2_FLG` `TRANS_FLG` **`SPI_SUBFI_FLG`** |
| **消息队列**(`_DTQ`)| 4 | `BLCOM_DTQ` **`CMD_DTQ`** `OIS_DTQ` `DATA_LATCH_DTQ` |
| **周期**(`_CYC`)| 2 | `USER_CYC` `OIS_CYC` |

表起始处的原始字节(`4001V020.plf`,文件偏移 `0x2bbc8`):

```text
0002bbc8  fb a0 03 10 91 44 06 10   49 4e 49 54 49 41 4c 5f   .....D..INITIAL_
0002bbd8  54 53 4b 00 44 41 54 41 5f 4c 41 54 43 48 5f 54 53   TSK.DATA_LATCH_TS
0002bbe8  4b 00 00 54 52 41 4e 53 5f 54 53 4b 00 00 00 45 58   K..TRANS_TSK...EX
```

第一个名字之前的 8 字节(`fb a0 03 10 91 44 06 10`)可按小端读作两个词
`0x1003a0fb` / `0x10064491` —— 与代码地址的量级一致,
即名字块之前可能有一个小的指针/计数头。这仅作为**观察**记录,尚未确证其结构。

### 28.3 跨型号:一次干净的平台二分

把这张表从 6 支镜头中都提取出来,得到的划分**与"变焦/定焦"无关**:

| 固件 | 镜头 | 类型 | `_TSK` | `_FLG` | `_DTQ` | `_CYC` | `SEM_` | 表区间 |
|---|---|---|---|---|---|---|---|---|
| `4001V020.plf` | S-R24105 | 变焦 | 9 | 7 | 4 | 2 | 2 | `0x2BBD0`–`0x2BCF0` |
| `4002V020.plf` | S-R70200 | 变焦 | 9 | 7 | 4 | 2 | 2 | `0x2FA40`–`0x2FB60` |
| `4006V020.plf` | S-E2470 | 变焦 | 9 | 7 | 4 | 2 | 2 | `0x1AFF0`–`0x1B110` |
| **`4003V020.plf`** | **S-X50** | **定焦** | **9** | **7** | **4** | **2** | **2** | `0x220`–`0x340` |
| `400CV020.plf` | S-S85 | 定焦 | 0 | 0 | 0 | 0 | 0 | — |
| `400EV020.plf` | S-S50 | 定焦 | 0 | 0 | 0 | 0 | 0 | — |

四支镜头**逐字共享全部 22 个资源名与 2 个信号量名**,
步长同为 288 字节,只是重新链接到了不同偏移。
另外两支**完全没有**。

### 28.4 `4003`(S-X50)是最有信息量的样本

`4003` 是**定焦**镜头,却带有**完整**的 RTOS 表 —— 所以这张表与变焦无关。
但它的**子系统符号塌缩了**:

| 固件 | OIS | Iris | Zoom | Focus | Motor | Gyro |
|---|---|---|---|---|---|---|
| `4001`(S-R24105)| 19 | 13 | 5 | 11 | 2 | 16 |
| `4002`(S-R70200)| 19 | 13 | 5 | 11 | 2 | 16 |
| `4006`(S-E2470)| 18 | 11 | 5 | 10 | 2 | 16 |
| **`4003`(S-X50)** | **4** | **0** | **0** | **0** | **0** | **0** |
| `400C` / `400E` | 0 | 0 | 0 | 0 | 0 | 0 |

`4003` 保留了**任务框架**,但几乎没有**执行器控制**符号。
与 §26 合起来看这是自洽的:RTOS 骨架是平台共用代码,
而 OIS / 光圈 / 变焦 / 对焦的参数集是随机构逐一套的。

### 28.5 这确立了什么

- 镜头固件是一个**多任务 RTOS**,而不是扁平的轮询控制循环:
  9 个任务、2 个信号量、7 个标志、4 个消息队列、2 个周期。
- **`CMD_TSK` + `CMD_DTQ`** 指向**命令通路** —— 一个从专用队列取消息的任务。
  这最可能是面向主机的命令分发器所在之处,
  也是分析镜头协议时最自然的切入目标。
- **`SPI_SUBFI_FLG`** 与 **`UART_FLG`** 点名了两个对外接口;
  `BLCOM_*` 则以任务 + 队列的形式点名了第三条通道。
  `SEM_MS_SUBFI` / `SEM_MS_SUBO` 是主机("MS")↔ 子功能通路的信号量。
- 6 支镜头里有 2 支**完全不带符号** —— 说明符号集是**构建期选项**,
  任何基于符号的结论都必须声明它对哪个平台成立。

```bash
python analysis/lens/rtos_resources.py firmware/

```
